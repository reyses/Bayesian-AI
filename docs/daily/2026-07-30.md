## Wakeup timer disabled minutes after shipping -- owner caught it's the wrong kind of trigger
Owner's immediate reaction to the just-built feature: "but there would be bias don't you think?" Correct on reflection: a realized-range threshold creates (1) corpus sampling bias -- decision points stop being uniformly distributed, skewed toward "right after a big move" -- and (2) a salience cue in its own right: even though the trigger is backward-looking, not predictive, the tool CHOOSING to interrupt there implicitly flags "this moment matters," which is close to the same category of problem the session's strict no-hints protocol exists to prevent. Presented both mechanisms plus 3 options (kill it / make it silent-log-only / keep as a known accepted bias) rather than defending the feature or deciding unilaterally.
Owner sharpened the critique further: "the only way it works is that it is a set pattern... valid if we look for a specific setup." This distinguishes OUTCOME-conditioned triggers (fire because a move turned out big -- retroactive selection) from STRUCTURE-conditioned triggers (fire on a pre-defined, validated setup, independent of how big the aftermath is) -- the same pre-registration discipline the project already applies to the edge gate itself. A magnitude threshold is definitionally the wrong kind.
Resolution: disabled the wakeup, both the live session (`wakeup 0`) and the code default (`WAKEUP_PT_DEFAULT` changed from 20.0 to 0.0) so it doesn't silently re-enable in a future session. The early-stop plumbing in `_advance` stays in place, unused, documented as ready to wire to a real structure-conditioned pattern if one gets properly validated later -- the wick-bias divergence threshold is the nearest candidate but is itself already flagged post-hoc/N=2, not trustworthy as a trigger yet. ## THE RATCHET WORKS — first significant positive result of the session
Owner framed the design correctly: *"this is the ratchet trailing stop — when should we stop letting it breathe and how hard should we ratchet"*, plus *"after 3 minutes have passed we should probably move trailing stop to 50% at least."* **Two implementation errors of mine had to be fixed before the mechanism was even observable.**
**Error 1 — a pure %-trail is narrower than one bar at small MFE.** At MFE=10pt a 20%-of-MFE trail leaves **2pt** of room, against 5s bars ranging 1–3pt. **Error 2 — the watch line was the stop line.** More fundamental: I had the observation level *at* the stop, so "price touches the 20% level" and "price stops out" were **the same event**. **Correct architecture**: stop loose at ~50% retracement (real protection, lets it breathe) · watch line at ~20% (observation only, never exits) · ratchet the stop to 10–20% when the watch line stalls or is multi-touched. Now fires 10–45% of the time.
